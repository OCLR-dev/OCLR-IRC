## 1. 已修訂的矛盾與缺漏

下表為文件審查發現，不是對尚未存在程式碼的執行驗證。高／中表示對後續設計的影響，不等同開發功能的 P0／P1。

| ID／影響 | 原問題 | 直接修訂 | 對應文件／任務 |
| --- | --- | --- | --- |
| R01／高 | requiredLocalChecks 是全域陣列，會要求開房先有 room_permission，也讓 Head To Head 需要顏色 | 改成按 intent 的物件及客戶端固定最低集合，分清本機 room_binding 與 P1 遠端 binding | context §5；CORE-01、INT-03、AC-18 |
| R02／高 | server-side UNKNOWN_MOD_POLICY 說要按目前地圖移除 start_game，但後端根本沒有 Bancho 目前地圖 | 後端只阻擋 entry；本機依目前 entry 檢查，全池無可選項才全域阻擋 | context §5.4；MAP-01、CTX-02 |
| R03／高 | 直播是否阻擋開賽沒有資料欄位，無法表達「核准的開賽前置規則」 | 增加明確 startPolicy.streamingRequirement；缺值阻擋，required／optional 有明確行為 | context §5；OCLR-01、AC-19；產品 D04 |
| R04／高 | context 不落盤，但聊天及操作日誌自動保存可能洩漏同一批私人名稱／地圖；開房崩潰又缺少可恢復記錄 | 私人聊天及完整日誌預設記憶體，使用者明確匯出；另列最小按帳號恢復記錄及清理，不保存指令 body | 專案 §4.2；LOG-01、CORE-01、AC-14／20；產品 D06 |
| R05／高 | SPEC-01 契約定版先於其必要的 SPIKE 驗證，且佇列恢復依賴的 LOG-01 卻反過來依賴 CORE | 新增 SPEC-00，SPIKE 後才 SPEC-01；LOG-01 改為中立記錄介面並成為 CORE-01 前置 | MVP §3／4；任務 DAG 重驗 |
| R06／高 | 手動 !mp 可繞過快捷操作佇列，且登入／切場次後的舊 HTTP 回應可能恢復已清掉資料 | 新增手動閘道、共同節流／序列化、應急優先序與 generation 檢查 | 專案 §6；MANUAL-01、INT-01／03、AC-17／20 |
| R07／高 | 宣稱必須 UID 配對卻沒有可靠查詢來源、API 或實作任務，可能永久卡住所有衍生操作 | 明列 P0 暱稱匹配不等於 UID 證明，另設產品決策 D05、SPIKE 證據及 PAIR-01 | 專案 §5；MVP §3；產品 D05 |
| R08／中 | pollAfterSeconds 禁止任何較快請求，與開房／Start 前的重讀衝突；serverTime 重新起算可能延長慢查詢快照 | 最小間隔只限週期輪詢，重要操作可單次合併重讀；新增 capturedAt，期限固定，stale 清理不被失敗延長 | context §3／5／6；INT-02、AC-19 |
| R09／高 | 單場失去角色與失去所有角色都回 403，客戶端無法決定清一場還是清全部 | 全域無裁判能力用 403；仍有其他能力但本場不可讀用不洩漏存在性的 404；明確區別 token expired 與 revoke | context §2／6／7；AUTH-02、CTX-01、AC-05 |
| R10／高 | S256 範例的 challenge 與 verifier 不相符；瀏覽器同意流程沒限定頂層導覽，若用 fetch 追 303 可能被攔 | 使用 RFC 公開配對向量；批准／拒絕用原生表單＋CSRF 與頂層 303，說明 JSON 例外 | 授權 §3–5；SPIKE-02、AUTH-01、AC-02 |

| R12／中 | 「所有 OCLR ID 為 UUID」與 slug／模板鍵矛盾；lobby 聲稱含模式但範例無欄位；完整範例又像被截斷的圖池 | 列出 ID 例外，模式只讀 rules，P0 binding 固定 null，完整範例改為真實完整的合成單圖系列 | context §1／5；CTX-02 |
| R13／中 | 工作估算與新增來源、身分配對、恢復及驗收工作未對齊，小範圍內測與公開簽章發行也混在一起 | 補齊任務、按工作量級重算，將交付類型列 D08；合成、真實整合與公開發行證據分開 | MVP §2–6；SPEC-00、PAIR-01、QA-01、RELEASE-01 |

## 2. 需要使用者確認的產品決策

以下皆為「待確認」。文件先採建議值方便評估，但保存／commit／push 草案不代表同意這些值。後續實作前由 SPEC-01 記錄確認結果，並同步修改四份文件。

| 決策 | 需要確認的問題 | 目前建議值 | 若採其他選項的影響 |
| --- | --- | --- | --- |
| D01：首版操作範圍 | MVP 是否只支援 osu! standard、Head To Head 1v1／Team VS、Score V2？ | 先限定這個矩陣；其他模式可讀與手動操作 | 擴大矩陣需增加規則、解析樣本、指令及跨平台演練；影響 SPEC-01、MAP-01、CONTROL-01、QA-01 |
| D02：登入期限與登出 | 是否接受 access 10 分鐘、未 refresh 2 小時／最長 12 小時；網站登出不自動撤銷桌面？ | 接受獨立 session，P0 重啟 App 重新授權，網站可撤銷裝置 | 若要求網站登出連帶撤銷或長期記住，需調整 session 關聯／安全儲存、refresh 及驗收；影響 AUTH、INT-01 |
| D03：Admin 場次範圍 | Admin 在桌面是否也只看本人被指派場次？ | P0 同樣限本人，完整管理留網站 | 若要跨場監管，需新增明確讀取範圍、投影／介面與測試，不能藉 Admin 暗中放寬既有 token |
| D04：規則與開賽前置 | 房名、出賽人數、NF／FM／Force Mod 及直播 required／optional 的核准設定由誰維護？ | 沿用 OCLR 對應工作人員管理能力；所有操作規則明確保存。建議直播為 optional，但正式賽事未填值仍視為未設定 | 請確認負責維護者及直播是否必須確認才開賽；選 required 會在未指派／改期未確認時阻擋 Start；影響 OCLR-01、CTX-02、CONTROL-01 |
| D05：帳號配對門檻 | 是否接受登入暱稱正規化相符＋裁判核對作為 P0 防誤操作門檻？ | 接受，UI 明示 nickname_matched 不等於 UID 證明；名稱不符／未知停用衍生變更 | 若一定要跨系統 UID 證明，SPIKE-01 需先找到可靠來源，再新增服務／契約與估算；不能以未驗證映射放行 |
| D06：記錄保存 | 是否接受聊天／完整操作記錄預設只存記憶體，手動匯出；僅最小恢復 ID 持久保存？ | 接受；最小記錄按帳號隔離，登出／撤權清理，7 天未用亦清除；不自動保存私人 context | 若需自動保存聊天，需定義保留期、加密／無金鑰行為及刪除介面；匯出檔無法遠端追回，影響 LOG-01 與驗收 |
| D07：單主控及重複開房 | 是否接受 P0 只有一個主控客戶端，尚無伺服器房間綁定／操作鎖？ | 接受；本機 pending／unknown 防重送，其他客戶端或人工開房仍可能重複 | 若同場多人主控必須首版支援，要把遠端綁定／協調契約及 write scope 提前至 P0，影響後端、核心及時程 |
| D08：首個交付型態 | 第一個交付是內部裁判測試版，還是具 Windows／macOS 簽章的公開版本？ | 先做三平台內部測試版，再完成公開簽章與更新發行；完整整合暫抓 8–12 週 | 請確認簽章資源可用性與交付目標；公開發行要完成簽章／公證等門檻，不以未簽內測包宣稱完成 |

工程可自行決定的項目包括模組內部命名、選定受支援的 Electron／SQLite driver 版本及 parser 實作方式；若變更使用者支援範圍、授權、保存政策或交付日期，須回到對應決策，不以工程細節取代產品確認。

## 3. 契約定版與後續流程

1. 使用者回覆 D01–D08 可集中在本文件記錄，不需要逐份修改同一政策。
2. SPIKE-01／02 只在未實作依賴的假設上蒐集證據；SPEC-01 依證據與必要回覆形成契約定版。
3. 所有新增 API／table／migration／App 模組均仍未實作；沒有真實授權及合成與實際驗收證據前，不宣稱已部署或已完成 MVP。
4. 授權、資料存取、正式賽果與遠端多主控協調維持不同邊界；實作時若新增 scope 或改變投影，更新契約及對應驗收。
